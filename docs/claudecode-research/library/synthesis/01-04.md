# 综合提炼：用户画像 01-04 模式、规避项与机会点

通过对“终端用户”、“管理员”、“生态开发者”与“集成商”四类典型画像的源码穿透，我们可以提炼出 Claude Code 在设计哲学、工程实现与商业潜能上的核心模式。

## 核心模式 (Patterns)

- **图谱引用**: [09-User Roles](../figures/09-user-roles.svg)

1.  **分层配置与策略继承 (Layered Config & Policy Inheritance)**
    - **源码事实**：`settings.ts` 显式合并了 Managed、User、Project、Local 四层配置。
    - **模式描述**：从组织意志到个人偏好的无缝叠加。这种分层不仅处理 UI 配置，更核心的是处理权限边界（Permission Mode）和功能开关（Policy Limits）。

2.  **计划与执行的显式解耦 (Separation of Plan & Execution)**
    - **源码事实**：`PermissionMode` 定义了 `plan` 模式，且 `EnterPlanModeTool` 是运行时的一等工具。
    - **模式描述**：通过模式切换而非提示词工程来控制风险。这降低了模型的认知负担，并为人类/审计系统提供了明确的干预点。

3.  **以 Transcript 为中心的持久化底座 (Transcript-Centric Persistence)**
    - **源码事实**：`sessionStorage.ts` 将所有消息、工具结果替换（Replacement）和子代理记录序列化为 JSONL。
    - **模式描述**：恢复（Resume）不是附属功能，而是基础设施。所有画像（无论是断点续传的终端用户还是需要审计的集成商）都依赖这一客观事实底座。

4.  **扩展即治理 (Extension as Governance)**
    - **源码事实**：Hooks、Skills 和 MCP 在 `ToolUseContext` 中汇流。
    - **模式描述**：扩展机制不仅是为了增加功能，更是为了在关键生命周期节点（如 `PreToolUse`）插入确定性的审计与拦截逻辑。

## 规避项 (Items to Avoid)

1.  **避免“单一交互表面”假设**
    - **规避理由**：源码证明了多路 Fast-path（bridge, daemon, remote）的存在。如果只针对 TUI 做优化，会丢失大量的自动化与远程协同场景。
2.  **避免“扁平化权限管理”**
    - **规避理由**：不同用户对风险的忍受度完全不同。严禁在全量环境默认开启 `auto` 模式，必须保留 `plan` 模式作为安全缓冲。
3.  **避免“黑盒化 Agent 决策”**
    - **规避理由**：`queryProfiler` 和 `transcript` 的存在说明了可观测性的重要性。不应隐藏 Agent 的思考过程和中间工具状态，尤其是在需要合规审计的画像（02, 04）中。
4.  **避免“无状态的自动化集成”**
    - **规避理由**：集成商画像显示，长任务需要会话持久化与状态恢复。简单的无状态 API 调用不足以支撑复杂的软件工程任务。

## 机会点 (Opportunity Points)

1.  **标准化 Bridge 协议与 SDK**
    - **潜力点**：目前 `bridge` 模式仍偏内部。如果能将其标准化为一套开放的 RPC 协议，将极大释放画像 04（集成商）的潜力，形成真正的“Agent 操作系统”。
2.  **基于 Hooks 的确定性合规插件**
    - **潜力点**：利用 `hooksConfigManager.ts` 暴露的丰富事件，可以开发针对特定行业（如金融、医疗）的代码合规与安全阻断插件，将治理能力转化为生态价值。
3.  **会话分支与多 Agent 协同 (Fork-Session 2.0)**
    - **潜力点**：深入挖掘 `fork-session` 机制，支持人类在不同分支上并行实验，或支持不同画像的 Agent（如 Security Agent vs. Feature Agent）在同一会话背景下协作。
4.  **智能预算与成本预测 (TaskBudget Optimization)**
    - **潜力点**：在 `queryLoop` 基础上增加更智能的成本预测模型，帮助管理员（画像 02）和集成商（画像 04）在任务开始前评估 Token 与时间投入。
