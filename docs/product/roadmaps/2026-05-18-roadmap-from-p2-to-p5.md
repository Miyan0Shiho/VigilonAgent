# Vigilon Agent 路线图讨论稿（P2-P5）

- 日期：2026-05-18
- 状态：讨论稿
- 目的：沉淀当前对 Vigilon Agent 后续开发路线的共识，作为后续给 Codex 下发任务时的总纲参考。
- 执行拆解：[2026-05-18 P2-P3 执行计划](./2026-05-18-p2-p3-execution-plan.md)

## 1. 总体定位

Vigilon Agent 的最终定位仍然是：

**任务优先的超级个人助手。**

但后续开发路线不直接围绕“超级个人助手能力清单”展开，而是分阶段推进：

1. 先把 Claude Code 风格的本地 Agent Runtime 做稳。
2. 再把能力彻底对齐 Claude Code。
3. 再把它产品化成可长期使用的 daily-driver 生产工具。
4. 再把能力上限推进到 Codex 级别。
5. 最后才进入 Vigilon 自己独有的上限探索。

这条路线的核心原则是：

- 先对齐成熟产品的 runtime 秩序，再做产品化，再做能力上限，再做差异化。
- 先解决“能不能稳定完成任务”，再解决“是不是足够好用”，最后再解决“能不能做到别人做不到的事情”。

## 2. 阶段定义

### P1：收尾 Solo Runtime Core Parity

P1 的定位已经确定，不在本文件中重新设计。

当前共识是：

- P1 由 Codex 持续推进收尾。
- P1 的正式定义是：**Claude Code Core Parity for Solo Runtime**。
- P1 的目标不是复刻 Claude Code 的企业产品面，而是复刻它的本地 runtime 闭环、执行秩序和安全边界。

P1 的主要参考文档：

- [2026-05-17 产品定位与能力边界](../2026-05-17-product-positioning-and-boundary.md)
- [2026-05-17 Phase 1 Solo Runtime Parity Checklist](../2026-05-17-phase-1-solo-runtime-parity-checklist.md)
- [2026-05-17 Phase 1 Copy-First Mechanism Map](../2026-05-17-phase-1-copy-first-mechanism-map.md)
- [2026-05-17 Phase 1 Development Baseline](../2026-05-17-phase-1-development-baseline.md)

### P2：能力彻底对齐 Claude Code

P2 的定位不是产品化，而是：

**把 Vigilon 的能力、机制和运行时语义，尽可能完整地推进到 Claude Code 核心能力级别。**

这意味着 P2 的目标不是“把能力链补齐”这么简单，也不是只做到“有这些模块、有这些工具、有这些入口”。

P2 真正要追求的是：

- 不是只有相似的能力名目，而是尽可能复刻 Claude Code 已被验证过的完整能力形态。
- 不是只有基础版、骨架版、可运行版，而是尽可能对齐 Claude Code 源码中的机制级实现思路。
- 不是只有“能工作”，而是尽可能对齐 Claude Code 的状态流、权限边界、失败语义、上下文治理和恢复链路。

换句话说，P2 追求的是：

**Claude Code 完整核心能力的机制级复刻与行为级对齐，而不是能力关键词对齐。**

P2 的重点方向包括：

- 搜索链路：不是只有 `Read / Grep / Glob` 可用，而是尽可能对齐 Claude Code 在搜索分层、上下文入口、结果裁剪、分页、读取补充和模型消费格式上的完整能力。
- 记忆链路：不是只有 transcript/resume，而是尽可能对齐 Claude Code 的 session memory、compact restoration、resume consistency、memory 注入与恢复秩序。
- `subAgent / Agent Tool`：不是只有能 delegation，而是尽可能对齐 Claude Code 的 agent definition、prompt 路由、任务交接、结果协议和会话边界。
- context governance：不是只有大输出截断，而是尽可能对齐 Claude Code 的 tool result budgeting、content replacement、compact boundary、post-compact restoration、上下文恢复一致性。
- skill / MCP / hook 运行时：不是只有能加载和调用，而是尽可能对齐 Claude Code 的 tool pool 组织、权限边界、运行时注入、错误展示和恢复语义。

P2 的目标不是“开始做花哨的新东西”，也不是“把 P1 的能力做得再多一点”，而是：

**尽可能完整地复刻 Claude Code 已经证明有效的核心能力。**

因此，P2 的完成标准不应表述为：

- “已经具备搜索、记忆、subagent、MCP、skills 这些能力”

而应表述为：

- “这些能力在 Vigilon 中，已经尽可能接近 Claude Code 源码里的真实能力水平、运行时秩序和行为语义”

### P3：产品化，做成生产工具

P3 的定位是：

**把已经具备 Claude Code 级能力的 Vigilon，做成一个真正好用、可落地、可长期使用的 daily-driver 生产工具。**

这意味着 P3 的目标不是“再加更多能力”，也不是“先做一个看起来像产品的 TUI 外壳”。

P3 真正要解决的是：

- 如何把 P2 中已经对齐好的 Claude Code 级能力，组织成一个你愿意每天真实依赖的主力工具。
- 如何让任务入口、执行过程、权限等待、错误恢复、结果交付和任务恢复形成低摩擦的日常工作流。
- 如何让 Vigilon 从“能力很强的 runtime”变成“你真正愿意长期使用的开发操作系统”。

换句话说，P3 追求的是：

**不是把能力做得更多，而是把能力做得可长期依赖、可形成习惯、可进入日常主工作流。**

P3 的核心方向包括：

- 一个可长期使用的 TUI，但 TUI 在这里是日常操作界面，而不是装饰性产品外壳。
- 更清楚的任务入口、任务状态、任务切换和任务恢复。
- 更清楚的工具执行反馈、权限等待、错误恢复和 operator 控制感。
- 更稳定的 transcript / resume / operator flow，让长任务、多任务和恢复任务都变得可依赖。
- 更好的结果交付和任务 handoff 体验，使每次任务结束都像交付物，而不是一段孤立回答。
- 自举开发能力：Vigilon 可以稳定帮助开发它自己的代码库，并进入自己的主开发链路。

P3 的完成标准也不应表述为：

- “已经有一个 TUI”
- “已经比 P2 多了几个产品功能”
- “看起来已经像一个产品”

而应表述为：

- “你愿意把真实开发任务默认先交给 Vigilon”
- “你知道它在做什么、卡在什么地方、等你做什么决定”
- “你在中断、报错、退出、恢复后，仍然信任它的任务状态”
- “它已经是一个你愿意长期依赖的主力开发工具”

因此，P3 的判断标准不是“能力比 P2 更多”，而是：

**它已经是一个你愿意真正每天使用、并逐渐替代其它开发 agent 入口的生产工具。**

### P4：实现其它产品的能力上限，从 Claude Code 走到 Codex

P4 的定位是：

**不再只是对齐 Claude Code，而是把能力上限推进到 Codex 这类更强产品的水平。**

这意味着 P4 的目标不是“在 P3 的产品上再加一些高级功能”，也不是“提前开始做 Vigilon 自己的独特方向”。

P4 真正要解决的是：

- 如何把 Vigilon 从 Claude Code 级的成熟本地 coding runtime，继续推进到 Codex 级别的能力上限。
- 如何让 Vigilon 不只是一个好用的 coding agent，而是开始具备更强的任务抽象、更深的检索与记忆、更复杂的自动化和更广的操作半径。
- 如何在已经是 daily-driver 生产工具的基础上，进一步获得“其它顶级 agent 产品已经证明可行的更高能力天花板”。

换句话说，P4 追求的是：

**不是开始定义 Vigilon 自己的独特价值，而是先把其它成熟产品已经展示出来的能力上限吃透。**

P4 的方向包括：

- 更强的深度搜索：不只是代码定位，而是更强的跨文件、跨语义、跨任务上下文的检索能力。
- 更强的长期记忆：不只是 session 级恢复，而是更稳定、可持续、可积累的长期工作记忆。
- 更高层的任务表达与执行，例如 `/goal` 风格能力：从“做一个动作”走向“围绕一个目标持续展开任务”。
- 自动化工作流：从单任务执行走向更复杂的任务串联、周期化和可恢复自动化。
- 桌面应用操作：把能力边界从代码仓库扩展到更广的本地工作流表面。
- 更复杂的 agentic orchestration：不只是 subagent，而是更高层的任务组织、协作与执行编排。
- 更强的研究与操作复合任务能力：把调研、推理、执行和交付更自然地串成同一条链路。

P4 的本质是：

**从 Claude Code 的成熟本地 coding runtime，进一步走到 Codex 所代表的能力上限。**

P4 的完成标准也不应表述为：

- “已经有深度搜索、长期记忆、桌面操作这些能力”
- “已经比 P3 多了一些高级 agent feature”
- “已经开始看起来像超级个人助手”

而应表述为：

- “Vigilon 已经不只是在 coding workflow 上接近 Claude Code，而是在能力上限上明显向 Codex 靠近”
- “它已经能承接更复杂、更长链路、更高抽象层级的任务”
- “它的能力半径已经从本地 coding runtime 扩展到更广的 agentic 工作流”

因此，P4 的判断标准不是“功能更多”，而是：

**它已经从 Claude Code 档位，明显迈向 Codex 档位。**

### P5 及以后：走出自己的上限

P5 才是：

**不再以 Claude Code 或 Codex 为主要参照，而是开始定义 Vigilon 自己独有的产品上限。**

这时才适合系统性讨论：

- Vigilon 独有的超级个人助手形态。
- Vigilon 自己的 Agent 社会。
- Vigilon 独有的工作流抽象。
- 其它产品没有解决好、但对你真实重要的问题。

## 3. 每一阶段各自回答什么问题

- P1：它能不能稳定闭环完成一个真实本地代码任务？
- P2：它的完整核心能力是否已经尽可能对齐 Claude Code？
- P3：它是不是一个你愿意每天真实依赖的生产工具？
- P4：它的能力上限能不能从 Claude Code 继续走到 Codex？
- P5：Vigilon 自己到底独特在哪里？

## 4. 阶段之间的关系

### P1 -> P2

P1 解决的是“地基是否成立”。

P2 解决的是“能力是否齐全”。

没有 P1 的稳定闭环，P2 会变成在脆弱 runtime 上不断叠复杂能力。

### P2 -> P3

P2 解决“能力是否已经足够完整地对齐 Claude Code”。

P3 解决“这些能力是否已经被组织成一个 daily-driver 产品”。

如果能力没补齐就先做产品化，很容易只做出一个更好看的半成品外壳。

### P3 -> P4

P3 解决“是否已经成为生产工具”。

P4 解决“能力上限是否还能继续提升到 Codex 档位”。

如果产品化没完成，就很难稳定验证更高阶能力是否真的有用。

### P4 -> P5

P4 仍然主要是在追平别人的上限，从 Claude Code 继续走到 Codex。

P5 才是开始定义 Vigilon 自己的上限。

这两者不能混在一起，否则会出现“既没追平成熟产品，又没形成自己特色”的中间态。

## 5. 当前明确不纳入主线的问题

以下方向在当前路线图里，不作为主线阶段目标：

- 企业账号体系
- 多用户 / 多组织治理
- enterprise admin
- billing / license / subscription
- commercial telemetry
- managed enterprise policy
- marketplace
- remote / bridge

这些能力不适合主导当前路线图，不应反向影响 P2-P4 的阶段定义。

## 6. 后续给 Codex 派任务时的判断规则

后续每个任务在进入实现前，建议先回答以下问题：

1. 这个任务属于 P1 收尾、P2、P3、P4，还是 P5 以后？
2. 这个任务是在补 runtime 核心能力、做产品化，还是冲击能力上限？
3. 这个任务是否直接服务于当前阶段的核心目标？
4. 这个任务是否会过早引入后续阶段的问题？
5. 这个任务的完成标准，是“模块存在”，还是“真实任务链路更强了”？

如果这些问题回答不清楚，就不应该立即进入实现。

## 7. 当前推荐的路线口号

- P1：稳闭环
- P2：对齐 Claude Code
- P3：做成 daily-driver 生产工具
- P4：走到 Codex
- P5：走出自己的上限

## 8. 用途说明

本文件不是最终产品 spec，而是当前路线图讨论稿。

它的主要用途是：

- 给你自己梳理后续阶段目标。
- 作为后续给 Codex 下发任务时的阶段判断依据。
- 避免任务实现再次滑回“什么都想做”的状态。
