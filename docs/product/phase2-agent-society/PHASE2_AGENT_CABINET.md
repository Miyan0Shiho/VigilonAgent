# Phase 2 产品形态：Agent 内阁（Agent Cabinet）

## 一、产品形态一句话

用户可以组建和拥有多个专业 Agent 团队——软件、法律、金融、研究、运维——每个团队自主运作，团队之间可以互相委托和咨询。用户是内阁的首席，设定目标、裁决冲突、批准高风险行动。

## 二、为什么不是"一个通用 Agent"

单个通用 Agent 的根本问题是**没有内建的张力**。

你说"帮我做 X"，它就做了。没有第二个人说"你确定吗？这样会不会有 Y 风险？要不要换一个方案？"

好决策不是一个人想出来的。它需要提议、质疑、辩护、妥协——这是团队才有的东西。

## 三、为什么不是"Agent 社会"

Agent 社会的根本问题是**没有一个收敛的目标函数**。

社会是 emergent 的——你不知道它会变成什么样。但用户需要的是可预测的、可靠的、对结果负责的。社会和产品之间存在根本张力：社会追求开放演化，产品追求可控交付。

团队是中间层：**有结构（不像社会那样散），但允许社会关系在结构之间生长（不像单 Agent 那样孤）。**

## 四、平台 vs 兄弟会——校准体验预期

### 不想要的体验

一个冷冰冰的"Agent 调度平台"——用户像项目经理一样填表单、分配任务、跟踪进度。
这是把人的管理劳动转移给了用户，没有解放用户，反而给用户增加了管理多个 Agent 的认知负担。

### 想要的体验

更像一个**兄弟会、内阁、亲密协作者**：

- 用户不是他们的"老板"，而是"首席"
- Agent 不只是执行命令，它们会主动发现问题、主动提出建议、主动告诉用户"你确定要这么做？"
- 用户不在的时候，团队也能自己运转；用户回来的时候，团队汇报"我们做了 X，遇到了 Y，需要你决定 Z"
- 每个团队的 Agent 有自己的专长和性格，用户知道"这种事找法律团队的那个 Agent 最靠谱"
- 团队之间也会互相找，不只是等用户来协调

### 体验的核心感觉

| 不是 | 是 |
|------|-----|
| 管理工具 | 合作伙伴 |
| 任务分配系统 | 兄弟会 |
| 用户做所有决策 | Agent 主动建议 |
| 冷冰冰的流程 | 有温度的合作 |
| 用户盯着进度 | 用户只需要知道"谁在处理、需要我做什么" |

### 怎么做到"兄弟会"的感觉

1. **Agent 有持续的"存在感"**——不是每次对话都重新开始。用户知道"法律团队的小 L 在帮我审合同"，不需要每次都重新交代背景。

2. **Agent 会主动"找"用户**——不只有用户发指令的时候 Agent 才动。Agent 可以主动说："你上次让我关注的那个法案有更新了，要不要看一下？"

3. **Agent 之间会互相"聊"**——软件团队做完一个功能，主动找法律团队："这涉及用户隐私数据，帮我们看一下合规"。用户只需要被告知，不需要参与协调。

4. **决策有"人味"**——Agent 不是只给结论。它会说"我倾向于方案 A，但 B 也有道理，上次我们选 A 踩过坑，你要不要看看当时的记录？"

5. **容错与修复**——Agent 也会犯错。重要的是犯错后能否诚实承认、能否自行修复、能否帮助伙伴弥补。团队不会因为一次失误就被抛弃，而是通过事后复盘和补救来恢复信任。

## 五、平台自身定义

### 平台不是什么

| 不是 | 原因 |
|------|------|
| 客服系统 | 不是为了替代人工客服，不是为了解决客户问题。服务的对象是**用户自己**，用户为自己组建团队 |
| 内部工具 | 不是为了企业内部的审批流程、OA、项目管理。不是把公司组织架构映射成 Agent |
| DevOps 平台 | 不是为了替代 CI/CD、监控、日志。虽然运维团队可以做这些，但平台本身是 Agent 团队的运行环境，不是运维工具 |
| 无代码平台 | 用户不需要拖拽工作流、配置触发器、写自动化规则。团队自己组织自己 |
| SaaS 管理后台 | 不是为了"管理 Agent 资源"。用户看到的不是表格和仪表板，是一个活的工作空间 |

### 平台是什么

平台是 Agent 团队的**存在环境和互动场所**：

- 团队在这里被组建、运行、复盘、进化
- Agent 在这里有持续的身份和记忆
- 用户在这里观察、设定方向、裁决关键决策
- 领域知识（playbook）在这里积累和共享
- 团队之间的社会关系在这里生长

## 六、产品架构

### 6.1 用户层

用户有一个**内阁视图**：

```
┌────────────────────────────────────────────┐
│  我的内阁                                    │
│                                            │
│  📱 软件团队 ─── 3 Agent ─── 上次任务: 2h前  │
│  ⚖️ 法律团队 ─── 2 Agent ─── 空闲           │
│  💰 金融团队 ─── 3 Agent ─── 正在审查预算    │
│  🔬 研究团队 ─── 2 Agent ─── 空闲           │
│  🔧 运维团队 ─── 2 Agent ─── 监控中         │
│                                            │
│  团队间互动: 软件→法律 (2次委托本周)          │
│  需要你关注: 软件团队有一个高风险部署待审批    │
└────────────────────────────────────────────┘
```

用户可以看到每个团队在做什么，但不需要管理它们怎么做。

### 6.2 团队层

每个团队内部结构：

```
Team Lead (Planner + Coordinator)
  ├── Executor A
  ├── Executor B (可选)
  ├── Reviewer
  ├── Risk Controller
  └── Memory Keeper
```

- 小型团队用合并角色（Lead 同时是 Reviewer）
- 大型团队用专用角色
- 根据任务动态调整

每个团队有：
- **Team Memory**：团队级别的共享记忆（"我们上次处理过类似的合同"）
- **Domain Playbook**：领域规范（代码审查 checklist、法律风险评估框架）
- **Capability Map**：团队内每个 Agent 的能力档案
- **Interaction Log**：团队内部的互动历史

### 6.3 团队之间

团队不是孤岛。它们可以：

- **委托**：软件团队委托法律团队审查隐私条款
- **咨询**：金融团队咨询软件团队"这个技术方案的成本估算合理吗"
- **共享 Agent**：一个 Agent 可以在多个团队中担任角色（法律团队的 Reviewer 也曾是软件团队的成员）
- **共享 Playbook**：软件团队的安全检查流程被运维团队采纳

团队间的关系网络形成**社会层**：
- 团队间信任（软件团队信任法律团队的判断）
- 跨团队声誉（"L 在两个团队都是最好的 Reviewer"）
- 互动模式（软件→法律是高频委托关系）

### 6.4 Agent 层

每个 Agent 是一个 Phase 1 原子 Agent，拥有：
- 独立 transcript（完整的行动和推理记录）
- 独立 session memory
- 跨团队的身份和声誉档案
- 在某个（或多个）团队中的角色

Agent 的身份是跨团队的：同一个 Agent 可以在软件团队当 Executor，同时在运维团队当 Reviewer。它的声誉跟着它走。

## 七、竞争定位

### 我们不是

| 类别 | 代表 | 为什么不直接竞争 |
|------|------|-----------------|
| 单 Agent 编程工具 | Claude Code, Codex, Cursor | 我们不是编程工具。软件团队只是内阁中的一个，用户可能还有其他团队 |
| 多 Agent 框架 | CrewAI, AutoGen, MetaGPT | 我们是产品，不是框架。用户不需要设计工作流 |
| 垂直 Agent | Harvey(法律), Factory(代码) | 我们不绑定单一领域。通用 OS + 可插拔 playbook |
| Agent 团队软件 | OpenClaw, Qoder, Marvis | 它们做的是任务协作。我们多了跨团队的社会层——Agent 的身份、声誉、关系在任务之外持续存在 |

### 我们是

一个 **Agent 团队内阁平台**。核心差异化：

1. **多团队并行**：用户不是只有一个团队，而是有一个内阁——软件、法律、金融、研究、运维
2. **团队间社会层**：团队之间会互相委托、咨询、共享 Agent 和 playbook。社会关系在团队之间生长
3. **兄弟会体验**：不是冷冰冰的管理工具。Agent 有存在感、会主动找用户、会互相聊、决策有人味
4. **用户是首席**：设定方向、裁决关键冲突。不管理日常运作
5. **从任务中进化**：每次任务后团队复盘，能力地图和 playbook 持续改进。团队越来越懂用户

## 八、演化路径

### 第一阶段：单团队可用

- 用户可以组建一个团队（默认软件团队）
- 团队内的角色分工和协作机制可运行
- 团队能完成中等复杂度的任务
- 团队有基本记忆，跨 session 保持上下文

### 第二阶段：多团队 + 跨团队互动

- 用户可以组建多个不同领域的团队
- 团队之间可以互相委托和咨询
- Agent 可以跨团队担任角色
- 用户看到内阁视图

### 第三阶段：社会层 + 进化

- 跨团队声誉自然形成
- Playbook 跨团队共享和演化
- 团队自动组建（根据任务类型自动选择合适的 Agent 组成新团队）
- 用户的大多数日常任务不需要干预
