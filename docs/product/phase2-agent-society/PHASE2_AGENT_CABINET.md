# Phase 2 产品形态：Agent 内阁（Agent Cabinet）

## 一、产品形态

用户可以组建和拥有多个专业 Agent 团队——软件、法律、金融、研究、运维——每个团队自主运作，团队之间可以互相委托、咨询、共享经验和人才。用户的角色不是"管理者"，而是"首席"——设定方向、裁决关键冲突、批准高风险行动，不干预日常运作。

## 二、为什么不是"一个通用 Agent"

单个通用 Agent 的根本缺陷是**没有内建的反对意见**。

你对它说"帮我做 X"，它就做了。没有第二个声音说："你确定吗？这样会不会有 Y 风险？有没有更好的方案？上次类似的事我们踩过坑。"

好的决策不是一个人闷头想出来的。它来自提议、质疑、辩护、修正、妥协——这些只存在于一个团队之中。

通用 Agent 的第二个问题是**没有分工**。一个再聪明的个体也有认知盲区。让它同时判断代码质量、法律合规、金融风险和用户体验，等于要求一个人同时是工程师、律师、会计师和产品经理。这不现实。

## 三、为什么不是"Agent 社会"

Agent 社会有它的位置——它是我们对长期愿景的判断。但作为当前产品形态，它有一个根本困难：**没有收敛目标**。

社会是涌现的——你不知道它会长成什么样子、谁会在什么时间形成什么关系。但用户需要的不是"观察社会演化"，而是"把事做成，并且下一次做得更好"。社会追求开放演化，产品追求可控交付。两者之间存在真正的张力。

团队恰好踩在这两者之间：**比社会有结构（你能知道谁在做什么、谁对什么负责），比单 Agent 有社会性（关系、信任、声誉在团队之间流动）。**

## 四、不想要的体验 vs 想要的体验

### 不想要的

一个冷冰冰的"Agent 调度台"。用户像项目部经理一样：填表单、分配任务、设置截止时间、跟踪每个 Agent 的进度、处理它们之间的冲突。

这不是解放用户，是把管理劳动从人类经理身上转移到了用户身上。用户没有少做任何事，只是换了一种形式继续做。

### 想要的

一个**兄弟会、内阁、亲密协作者网络**。

这种感觉很难用功能列表描述，但它包含这些瞬间：

- 你早上打开电脑，不是面对一个空白聊天框，而是看到"昨晚软件团队完成了部署，法律团队标记了一个需要你确认的条款，研究团队找到了三篇和你上周讨论相关的论文"
- 你对软件团队说"帮我加一个功能"，不是立刻开始写代码，而是团队内部先讨论——有人提议方案、有人质疑风险、有人建议先问问法律团队——然后 Planner 回来说"我们倾向于方案 A，但有两点需要你确认"
- 你不确定某个决策做得好不好，不是自己去翻聊天记录，而是 Memory Keeper 说"上个月我们做过类似的，当时的选择和结果都在这里，你可以参考"
- 你不在的时候团队也能自己转；你回来的时候，团队汇报"我们做了 X，遇到了 Y，需要你决定 Z"，而不是"在等你指令"
- 团队之间互相找——软件团队做完功能主动找法律团队说"这个涉及隐私数据，帮我们看一下"，你不需要做这个协调

### 核心感觉

| 不是 | 是 |
|------|-----|
| 管理工具 | 合作伙伴 |
| 任务分配系统 | 兄弟会 |
| 用户驱动所有决策 | Agent 主动提出并论证方案 |
| 冷冰冰的流程引擎 | 有温度、有判断力的合作 |
| 用户盯着进度条 | 用户只需要知道"谁在处理、我要做什么" |

### 怎么做到"兄弟会"的感觉

**Agent 有持续的存在感。**不是每次对话都从零开始。用户知道"法律团队的小 L 在帮我审那三份合同"，不需要每次都重新交代背景、文件、截止日期。Agent 不在线也不等于"消失"——它有持续的身份和记忆。

**Agent 会主动"敲门"。**不是只有用户发指令的时候它们才动。Agent 可以主动出现说："你上周让我盯的那个法案出新版本了，变化摘要和影响分析做好了，要不要现在看？"

**Agent 之间会互相"串门"。**软件团队做完一个功能，主动找法律团队："这个涉及用户隐私数据的存储和跨境传输，帮我们做一下合规审查。"用户只需要被告知结果，不需要参与协调。这种团队间的自主互动是"社会感"的来源——不是用户一个人连线所有 Agent，而是 Agent 之间也有连接。

**决策过程有"人味"。**Agent 不只是一个结论。它会说："我倾向于方案 A，但说实话 B 也有道理。上次我们选 A 的时候踩过一个坑，那次是因为测试覆盖不够。这次如果我们选 A，需要先把测试补上。你要看看当时的记录吗？"

**容错与修复。**Agent 也会犯错。真正重要的是它能否诚实承认、自行修复、以及在修复后帮助其他人避免同样的错误。团队不会因为一次失误就被用户换掉——真正的信任来自"我们一起处理过问题，我知道你下次会更好"。

## 五、平台自身定义

### 平台不是

| 不是 | 原因 |
|------|------|
| 客服系统 | 服务的对象不是"客户的工单"，是**用户自己**。用户为自己组建团队 |
| 企业内部工具 | 不是公司 OA、审批流、项目管理。不是把组织架构映射成 Agent |
| DevOps 平台 | 运维团队可以做监控和告警，但平台本身不是 CI/CD 或日志系统 |
| 无代码平台 | 不需要用户拖拽工作流、配触发器、写自动化规则。团队自己管自己 |
| SaaS 管理后台 | 用户看到的不是表格和仪表板，是活的工作空间 |

### 平台是什么

平台是 Agent 团队的**存在环境和互动场所**。团队在这里被组建、运行、复盘、进化；Agent 在这里有跨越单次任务的持续身份和记忆；用户在这里观察社会状态、设定方向、裁决关键决策；领域知识在这里被积累、验证、共享和迭代；团队之间的信任和声誉也在这里生长。

它不是"Agent 的管理系统"。它更像是"Agent 们的城市"——提供基础设施、公共空间、法律框架、社交网络，但每个团队和每个 Agent 在里面有自己的生活。

## 六、产品架构

### 6.1 内阁视图（用户界面）

用户的核心交互界面不是聊天框，而是**内阁仪表板**：

```
┌──────────────────────────────────────────────────┐
│  我的内阁                                          │
│                                                  │
│  📐 软件团队 · 4 Agent · 上次任务: 2 小时前        │
│     当前: 正在处理 API 重构                        │
│                                                  │
│  ⚖️ 法律团队 · 2 Agent · 空闲                     │
│     最近: 审阅了 3 份隐私条款                       │
│                                                  │
│  💰 金融团队 · 3 Agent · 正在工作中                 │
│     当前: 审查 Q2 云成本预算                        │
│                                                  │
│  🔬 研究团队 · 2 Agent · 空闲                     │
│     最近: 竞品分析报告已完成                        │
│                                                  │
│  ──────────────────────────────────────          │
│  团队间动态:                                       │
│  软件 → 法律  本周 2 次委托（隐私合规审查）          │
│  金融 → 研究  本周 1 次咨询（竞品定价分析）          │
│                                                  │
│  ⚠ 需要你关注:                                    │
│  软件团队有一个高风险生产部署待审批                  │
│  法律团队标记了一份合同的关键条款需要你确认            │
└──────────────────────────────────────────────────┘
```

用户可以点进任何一个团队查看详情，也可以直接对整个内阁说"帮我做 X"。内阁自己判断哪个团队来处理、是否需要多个团队协作。

### 6.2 团队内部结构

每个团队内部不是平权民主，也不是单人独裁。它有一个自然的层级：

```
Team Lead（规划者 + 协调者）
  ├── Executor A          ← 执行者
  ├── Executor B（可选）   ← 并行执行者
  ├── Reviewer             ← 审查者
  ├── Risk Controller      ← 风控者
  └── Memory Keeper        ← 记忆员
```

一个小团队可能只有 2 个 Agent，角色合并（Lead 兼 Reviewer，Executor 兼 Memory Keeper）。一个大团队可能每个角色都是独立 Agent。角色不是写死的，根据任务自动分配和调整。

每个团队拥有四样东西：

- **团队记忆**：不是某个 Agent 的私有记忆，而是团队共享的——"我们上次处理过类似的合同纠纷"、"这个模块的测试在重构时最容易出问题"
- **领域手册（Domain Playbook）**：这个领域的检查清单、常见风险、判断框架、标准做法。代码团队有代码审查 checklist，法律团队有条款风险矩阵，金融团队有预算审查框架
- **能力地图**：团队内每个 Agent 擅长什么、容易在哪类问题上犯错、和其他 Agent 的配合效果如何
- **互动日志**：团队内部的决策记录——谁提议了什么、谁反对了、最终怎么决定的、后来证明是对是错

### 6.3 团队之间（社会层）

这是"内阁"区别于"多 Agent 任务编排"的关键层。团队不是孤岛：

- **委托**：软件团队需要隐私合规审查，不是用户去协调——软件团队的 Lead 直接向法律团队发起委托，附上需要审查的文件和上下文
- **咨询**：金融团队在做成本估算时不确定某个技术方案的合理性，直接问软件团队"这个估算是合理的吗？"
- **人才流通**：一个 Agent 可以属于多个团队。法律团队的 Reviewer 曾经是软件团队的成员，它对代码有理解，这让它的法律审查比纯法律 Agent 更精准
- **知识流通**：软件团队发现了一个安全检查流程很有效，这个流程可以被运维团队采纳。它不是某个团队的私有财产

团队间的关系构成真正的社会层：

- 团队间信任："软件团队每次都把文件准备得很清楚，法律团队可以快速审查"
- 跨团队声誉："L 在两个团队里都是最好的 Reviewer，下次组新团队找 ta"
- 稳定的互动模式：某些团队天然高频互动（软件↔法律），某些团队偶尔互动（研究↔运维）

### 6.4 Agent 层

每个 Agent 是 Phase 1 的原子 Agent——独立的 transcript、session memory、权限、loop。Phase 2 不重新定义 Agent，而是在 Agent 之上叠加：

- **团队角色**：在某个（或多个）团队中担任的角色
- **跨团队声誉**：不随团队变化而消失的身份档案
- **社会记忆**：不只记住"自己做了什么"，也记住"和谁合作过、谁值得信任、谁曾经提供过关键帮助"

## 七、竞争定位

### 竞品概览

| 类别 | 代表产品 | 我们与之的差异 |
|------|---------|-------------|
| 单 Agent 编程工具 | Claude Code、Codex、Cursor | 我们不是编程工具。软件团队只是内阁中的一个，用户还可以有法律、金融、研究团队 |
| 多 Agent 编排框架 | CrewAI、AutoGen、MetaGPT | 它们是框架，用户（开发者）需要自己设计工作流和 prompt。我们是产品，团队自组织 |
| 垂直领域 Agent | Harvey（法律）、Factory（代码） | 我们不做单一垂直领域。通用 OS + 可插拔 playbook 让我们可以跨领域 |
| Agent 团队工作软件 | OpenClaw、Qoder、Marvis | 最接近的竞品。它们的核心是"任务协作"——多个 Agent 一起完成一个任务。**我们的核心差异是"社会层"**——Agent 的身份、声誉、关系在任务之外持续存在，团队之间会自己建立联系，不只靠用户协调 |

### 核心差异化

1. **多团队并行，而非单团队协作。** 用户拥有一个内阁——软件、法律、金融、研究、运维团队同时存在。不同的事找不同的团队，复杂的事由多个团队协作
2. **团队之间存在真正的社会关系。** 不是靠用户在中间协调，而是团队之间自己发现"我需要法律团队帮我看这个"，自己委托，自己传递上下文
3. **兄弟会体验，而非管理工具。** Agent 有持续的存在感、会主动找用户、会互相沟通、决策过程有判断和解释。用户的感觉是"我有一个可靠的内阁"，而不是"我在管理一堆 AI 员工"
4. **用户是首席，不是经理。** 用户的核心动作是：设方向、做选择、批高风险。不需要拆任务、盯进度、做协调
5. **从每次任务中持续进化。** 团队复盘、能力地图更新、playbook 迭代。团队越来越懂用户，用户越来越信任团队

## 八、演化路径

### 阶段一：单团队可用（MVP）

用户有一个团队（默认软件团队）。团队内部有基本角色分工和协作流程。能独立完成中等复杂度的任务。跨 session 保持上下文和记忆。**这一阶段证明：Agent 团队比单 Agent 更可靠。**

### 阶段二：多团队 + 跨团队互动

用户可以组建多个不同领域的团队。团队之间可以互相委托和咨询。Agent 的身份和声誉跨团队流动。用户看到内阁视图，能看到每个团队的状态和团队间的互动。**这一阶段证明：多团队内阁比单团队覆盖更多用户场景。**

### 阶段三：社会层 + 自动组队

跨团队声誉网络自然形成。Playbook 跨团队共享和演化。系统能根据新任务类型自动判断需要什么团队结构、从现有 Agent 中挑选合适的人选组建临时团队。用户的大多数日常任务不需要主动干预。**这一阶段证明：Agent 团队能自我进化，用户从"使用工具"变成"与内阁共事"。**
