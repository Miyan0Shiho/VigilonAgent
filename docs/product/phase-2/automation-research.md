# Codex 自动化：任务调度与持续运行

调研日期：2026-05-27
参考：Codex Heartbeats、OpenClaw Task Brain、kage

## 定位

Codex 的"自动化"和 `/goal` 不是同一件事。

- **`/goal`**：用户给一个目标 → Agent 循环执行直到完成 → 停止。一次任务。
- **自动化**：Agent 作为持续运行的 worker，自己决定什么时候醒来、检查什么、要不要行动。不是"跑一次"，是"一直在线，周期性工作"。

用户觉得这和 OpenClaw 很像——判断是对的。两者都是把 Agent 当作**可调度的持续运行实体**，不是一次性工具调用。

## Codex Heartbeats

### 心跳调度

Agent 设置自己的检查节奏，不是外部 cron：

- **可配置节奏**：每 15 分钟 / 每小时 / 每天早上一次
- **活跃时间窗口**：只在工作日 9-18 点运行，周末不打扰
- **读优先默认**：自主运行期间默认只读——写操作（发邮件、改文件、调 API）需要显式白名单授权
- **路由目标**：心跳触发后的行动有明确的 routing target，不会乱跑

### 典型场景

- 每 15 分钟检查一次 Slack → 看有没有需要回复的消息 → 草稿回复 → 标记优先级 → 不下发（等人审批）
- 每天早上检查 GitHub issues → 判断是否有需要关注的 → 汇总报告
- 监控 CI 构建状态 → 失败时自动查看日志 → 判断是否能自动修复 → 不能则升级给人

### 自调度

Agent 在执行任务过程中可以给自己设未来的检查点：
- "这个部署需要 2 小时，2 小时后我来检查构建结果"
- "这个 PR 等 review，明天早上我来检查有没有人回复"

不是人在外面设 cron，是 Agent 自己根据任务上下文决定"我需要在未来某个时刻再做这件事"。

## 线程持久化

每次心跳醒来，Agent 复用之前的对话线程——不丢上下文。

- 线程是 Codex 的对话单元，同一线程内的 Agent 记得之前做了什么
- 跨天、跨周的任务，上下文持续累积
- 和 Chronicle（录屏 → 视觉记忆）是两套系统——Chronicle 是"看到什么"，线程持久化是"说过什么、做过什么"

## OpenClaw Task Brain（对照参考）

OpenClaw v2026.3.31 做了统一任务账本，比 Codex 更系统化：

### 统一 SQLite 账本

原来四种执行路径各自为政，统一成一条 SQLite 表：

| 路径 | 场景 |
|------|------|
| ACP subagent | 主 Agent 派发的子任务 |
| Cron | 定时触发（"每天早上 9 点"） |
| Background CLI | 用户在终端手动启动的后台任务 |
| Subagent | 程序化启动的子 Agent |

### 统一生命周期

- **心跳监控**：所有任务有统一的心跳检测 → 丢了的自动恢复
- **阻塞持久化**：任务可以在 `blocked` 状态持久化到磁盘，等条件满足后在**同一 flow** 上重试——不留孤儿进程
- **父子关系**：任务有 parent-child 关系，结果可追溯到原始对话
- **CLI 管理**：`openclaw flows list|show|cancel`

## kage（轻量参考）

开源工具 kage 走另一个极端——零后台开销：

- 用系统 cron/launchd 定时启动 AI CLI
- 唤醒 → 执行 → 退出，不留常驻进程
- Markdown + YAML front matter 定义任务
- 支持 `suspended_until`（阻塞到某条件解除）、`allowed_hours`（时间窗口）、执行模式（`continuous` / `once` / `autostop`）

## 对 Vigilon 的启示

做任务调度需要三样东西：

1. **任务账本**：SQLite 或文件系统上的持久化任务记录——任务 ID、状态（active/blocked/done/failed）、父任务、创建时间、下次检查时间、关联的 session/线程
2. **自调度原语**：Agent 在执行过程中可以 `schedule(future_check)`——"2 小时后检查构建结果""明天早上检查 PR review 状态"
3. **心跳循环**：一个轻量的调度循环——到时间 → 加载任务上下文 → Agent 判断是否需要行动 → 行动或跳过 → 更新下次检查时间

这些不碰 agent loop 核心——是在 agent loop 外面加一层**调度基础设施**。
