# Phase 2 问题域重构

重构日期：2026-05-27
重构原因：19 个问题域中约 1/3 混淆了产品问题与社会/行业问题；自进化作为三大目标之一被埋没在子问题中；存在结构性盲区

---

## 重构原则

1. **三大目标各有一级问题域对应**。自进化、感知、安全——每个目标至少有一个独立的一级领域。
2. **只纳入 Vigilon 可控的问题**。行业标准、法律法规、社会趋势是背景，不是产品问题域。
3. **合并同质领域**。意图形成(1)、需求协商(2)、适应性引导(3)本质上是同一件事。
4. **补上盲区**。onboarding、用户纠错、跨 session 连续性、Agent 数量爆炸、失败模式分类法、多模型适配、安全摩擦成本。
5. **每个领域回答一个核心冲突**。不给描述性标题，给需要解决的矛盾。

## 七大问题域

---

### A. 意图理解与适应性引导

> **核心冲突**：聊天框假设用户已有清晰意图。真实用户只有情境、焦虑和模糊愿望。Agent 需要在用户说不清楚时帮他想清楚，在方向有风险时敢质疑，在用户知道要什么时不挡路。

**服务于**：Goal 1（感知）

**子问题**：

- **A1. 意图发现**：Agent 能否从用户环境（文件、项目、历史、工作模式）中主动发现"你可能需要做 X"？而不是永远等用户先开口？

- **A2. 意图翻译**：用户说"帮我优化一下这个系统"——Agent 如何判断是性能优化、架构重构还是代码清理？如何在不要求用户写 prompt 的前提下完成翻译？

- **A3. 需求质询**：Agent 能否在执行前判断需求不成熟、自相矛盾或 ROI 不合理？能否提出替代方向，并在必要时说"这个方向有风险，因为 X"？

- **A4. 适应性介入**：系统如何判断当前用户需要什么密度的引导——代办、陪跑、质询还是放权？判断错了怎么办（把专家当新手 / 把新手当专家）？如何避免引导变成打扰？

- **A5. 前 5 分钟与能力发现**：用户第一次打开 Vigilon，完全不知道 Agent 能做什么。最初体验是什么？随着 Agent 和 skill 增长，用户如何发现"我可以用什么"？

- **A6. 用户纠错**：Agent 走错方向时，用户如何用最小交互成本纠正——而不是重新描述整个任务？Agent 如何从一次纠正中学会"这个用户的这类表述通常指 X 而不是 Y"？

**Phase 2 范围**：
- 做：环境感知基础层（文件/项目/history）、意图翻译（模糊→具体）、需求风险 checklist、介入阈值滑块、纠错快捷操作
- 不做：完整 onboarding 向导、跨领域熟练度推断、主动建议系统

### B. 信念、知识与记忆架构

> **核心冲突**：Agent 行动依赖大量"知识"——网页上看到的一句话、用户随口说的偏好、模型幻觉生成的结论、三周前过期的 API 文档——全部以相同可信度混在 memory 里。Agent 需要知道自己知道什么、怎么知道的、有多确定、什么时候过期。

**服务于**：Goal 2（认知架构是自进化的基础）、Goal 3（错误信念是安全事故的主要根因）、Goal 1（记忆是理解用户的前提）

**子问题**：

- **B1. 信念注册**：每个关键信念是否携带来源（observation / inference / testimony / authority）、证据强度（0-1）、认知类别（事实 / 推断 / 假设 / 计划 / 偏好）、适用边界和过期条件？不确定性如何在 compact 和 Agent 交接中保留，而不是被 summary 抹平成确定性陈述？

- **B2. 记忆所有权与生命周期**：哪些记忆属于用户（可导出/删除）、项目（共享）、组织（合规管理）、Agent（会话级）、工具（环境配置）？用户如何看到、质疑、修复、迁移或删除影响 Agent 行为的记忆？

- **B3. 记忆版本控制**：记忆会演化——偏好改变、约束更新、旧知识被取代。用户能否看到记忆变更历史？能否回退到"三天前的记忆状态"？

- **B4. 外部污染防护**：网页、邮件、工具输出中的内容如何避免自动进入长期记忆？自动总结和 consolidation 如何避免把不可靠来源的信息洗成"事实"？

**Phase 2 范围**：
- 做：belief registry 基础结构（source/evidence/epistemic category/expiry）、记忆所有权模型、外部内容门控
- 不做：AGM 形式化信念修正、记忆跨平台迁移标准

### C. 规划与长程连续性

> **核心冲突**：Agent 任务可能持续 16 小时、经历数百次 compact、跨越多次用户上下线。每次上下文死亡都可能丢失目标、约束和关键决策理由。当用户第二天回来，需要在 30 秒内理解"昨天做到哪了，今天该做什么，有什么风险"。

**服务于**：Goal 2（长任务是 Agent 团队的典型场景）、Goal 1（目标不漂移 = 用户意图不丢失）

**子问题**：

- **C1. 不可压缩核心**：每次 compact 时，哪些信息必须原样保留——原始目标？关键约束？已做的决策和理由？未验证假设？如何验证 compact 后关键约束没有丢失？

- **C2. Objective Drift 检测**：数百次 compact 后，如何检测当前行动向量已偏离原始目标？谁来检测——Agent 自己（可能不自知）还是独立视角？

- **C3. Life Segment 分解**：长任务如何拆成可恢复、可审计、可交接的 life segments？每个 segment 需要什么 state snapshot？

- **C4. 跨 Session 人-Agent 连续性**：用户下线 8 小时回来后，Agent 如何快速重建上下文？不是 dump 所有信息，而是结构化的"现状摘要 + 待决策事项 + 风险提示"。

- **C5. 动态规划**：Plan 是否携带 horizon、confidence、risk、cost 和 pivot condition？什么证据触发重规划？如何避免"因为已经投入所以继续"的沉没成本陷阱？

**Phase 2 范围**：
- 做：三层信息分类（objective/decisions/beliefs）、drift 检测、life segment checkpoint、plan metadata、session 恢复摘要
- 不做：约束校验和的密码学证明、自动沉没成本检测

### D. 自进化与持续学习

> **核心冲突**：Agent 不能只是执行任务——它需要从每一次成功和失败中学习，让下一次做得更好。但"学习"在 Agent 语境下极其危险：学到的可能是错误归因、可能过拟合到特定场景、可能静默退化。自进化的核心不是"能不能学"，而是**学了什么、怎么验证学到了、学错了怎么回退**。

**服务于**：Goal 2（核心战场——这就是"自进化自学习"本身）

**子问题**：

- **D1. 经验提取与泛化**：Agent 如何从单次成功/失败中提取可复用模式？如何区分"这次碰巧做对"和"这个方法普遍有效"？如何避免从失败中学到错误归因——"上次用 X 失败了，所以永远不要 X"——但 X 在另一种情境下可能是对的？

- **D2. 技能进化**：Agent 的能力如何随时间提升——不是靠人更新 prompt，而是靠系统从执行轨迹中识别可复用模式、验证、泛化、部署？SkillClaw (arXiv:2604.08377) 展示了跨用户轨迹聚合和技能传播的可行性——Vigilon 如何做到类似的事？

- **D3. 知识代谢**：新知识如何经过"候选 belief → 验证 → 整合 → 提升" pipeline，而不是直接写入长期记忆？Agent 如何发现已有知识已经过期？知识如何降权、遗忘、更新？这本质上是信念架构(B)的动态面。

- **D4. 进化验证与回退**：如何验证一次进化确实让 Agent 变好了——而不只是在新场景上看起来好，在旧场景上静默退化？进化历史如何像 git history 一样可追溯、可 diff、可回退？进化后必须在哪些核心场景上回归验证？

- **D5. 行为漂移检测**：模型更新、prompt 调整、memory 积累、tool 变更后，Agent 行为是否发生了不应有的变化？如何检测"任务 A 的能力提升了但任务 B 下降了"或"能力没变但安全性下降了"的 tradeoff？

- **D6. 跨用户泛化与隔离**：从一个用户的使用中提取的经验，能否安全地泛化到其他用户？什么可以共享（通用技能、工具使用模式、故障排查经验），什么必须隔离（个人偏好、隐私数据、特定项目上下文）？

- **D7. 失败模式驱动的进化**：Agent 有哪些系统性失败模式——目标错误泛化、确认偏差放大、模式崩塌、奖励黑客、级联失败、分布外失效？进化机制如何针对这些失败模式做定向改进，而不是"平均来说变好了一点"？

**Phase 2 范围**：
- 做：经验记录结构（成功/失败 + 上下文 + 根因标记）、基本进化验证（核心场景回归）、行为漂移检测、知识代谢 pipeline
- 不做：自动经验泛化、跨用户 skill 传播、自动失败模式识别

**研究基础**：
- EVOCHAMBER (arXiv:2605.11136) — 个体/团队/群体三层协同进化 + CODREAM 协同反思
- TacoMAS (arXiv:2605.09539) — 快慢双环：能力每轮更新，架构每 K 轮更新
- LIFE Survey (arXiv:2605.14892) — Lay→Integrate→Find faults→Evolve 四阶段
- Fujitsu 自进化多 Agent (May 2026) — 制造业/医疗/金融场景，+28 点准确率
- SkillClaw (arXiv:2604.08377) — 跨用户轨迹聚合 + skill 集体进化
- GRAFT-ATHENA (arXiv:2605.11117) — 自改进 Agent 团队自主扩展行动空间

### E. 多 Agent 协作

> **核心冲突**：多个 Agent 协作不是"启动更多 worker"。它同时引入信念冲突、责任模糊、通信复杂度 O(n²)、污染传播和资源争抢。3 个 Agent 的治理和 30 个 Agent 的治理是完全不同的问题。

**服务于**：Goal 2（Agent 团队的协作层）、Goal 3（多 Agent 是最大的安全挑战之一）

**子问题**：

- **E1. 冲突与异议治理**：多 Agent 结论冲突时，谁有权合并？异议如何保留（minority opinion）而不是被悄悄丢弃？Agent 之间如何背书（"基于证据 E，我担保结论 C"）和质疑（"结论 C 的假设 A 在场景 S 下不成立"）？

- **E2. 交接协议**：Agent A 把工作交给 Agent B 时，传递什么——裸结论？还是完整 belief history + 未验证假设 + 风险摘要 + failed attempts？上游 Agent 的错误导致下游行动失败时，责任链如何追溯？

- **E3. Agent 数量爆炸**：3 个 Agent → 30 个 Agent，通信复杂度、信念污染风险、资源死锁、用户注意力过载全部指数增长。是否需要 Agent 层级（coordinator / worker / reviewer）？层级是静态配置还是动态形成？

- **E4. 团队组成与编排**：不同任务需要不同类型的 Agent 团队——谁来组队？用户手动指定还是系统自动编排？自动编排时如何选择 Agent 类型、数量和通信拓扑？

- **E5. 人类在回路中的位置**：多 Agent 协作时，人类是什么角色——审批者、观察者、参与者还是完全离线？什么信号必须升级给人，什么可以 Agent 间自行解决？

**Phase 2 范围**：
- 做：Agent-to-Agent 冲突协议、交接 package 标准、基本层级（coordinator/worker）、人工升级信号
- 不做：自动团队编排、动态拓扑优化、跨组织 Agent 协作

**研究基础**：
- EVOCHAMBER — 4-5 个稳定 niche specialist 从相同初始化 Agent 中涌现
- TacoMAS — 团队架构每 K 轮根据演化博弈论更新
- POLARIS (SEAMS 2026) — Adapter→Reasoning→Meta 三层自适应

### F. 运行时安全与信任边界

> **核心冲突**：Agent 的攻击面远大于聊天机器人——外部内容、工具调用、记忆存储、Agent 间通信，每个都是攻击向量。但防御太重的系统会被用户绕过——安全机制必须可用。假阳性（把正常操作当攻击拦了）可能比漏过一次攻击更破坏信任。

**服务于**：Goal 3（核心战场）、Goal 1（用户信任的前提）

**子问题**：

- **F1. 信任边界架构**：所有外部输入（网页、工具输出、Agent 间消息、邮件、文档）如何通过统一的信任边界进入系统？边界内做什么——指令剥离、来源标记、内容与指令的强制分离？

- **F2. OWASP ASI 对齐**：如何防御 10 类攻击——Goal Hijack、Tool Misuse、Identity Abuse、Supply Chain、Code Execution、Memory Poisoning、Inter-Agent Comms、Cascading Failures、Trust Exploitation、Rogue Agents？每一项在 Vigilon 架构中对应什么防御点？

- **F3. 安全摩擦成本**：安全检查太频繁 → 用户习惯性点"同意"→ 安全形同虚设。安全检查太严格 → 用户关掉安全机制 → 完全没有保护。如何让安全分级——什么时候静默通过、什么时候请求确认、什么时候强制阻断？

- **F4. 假阳性代价**：把正常指令误判为攻击并拦截 → 任务中断 → 用户不信任安全机制 → 下次直接绕过。安全机制的 precision/recall 如何平衡？假阳性后用户如何快速 override 并让系统记住"这类操作是安全的"？

- **F5. 攻击后隔离与清洗**：被攻击后，如何隔离受影响 session？如何扫描和清洗被污染的 memory、belief、artifact？如何从 clean checkpoint 恢复？

- **F6. 浏览器 Agent 安全**：Agent 浏览网页时，如何区分用户指令和网页内容？如何防止网页中的隐藏指令被当作系统指令执行？浏览上下文和信念上下文如何隔离？

**Phase 2 范围**：
- 做：输入信任边界、指令来源分离、OWASP ASI 对齐的基础防御、安全摩擦分级（静默/确认/阻断）、攻击后隔离、浏览器 context 分离
- 不做：完整 defense-in-depth、自动攻击检测和响应、Agent identity 行业标准

**研究基础**：
- OWASP Top 10 for Agentic Applications 2026
- NIST CAISI RFI on securing AI agent systems
- Microsoft Agent Governance Toolkit — 10/10 OWASP ASI, sub-ms 策略执行
- AgentShield — 框架无关 5 层防御中间件
- Five Eyes "Careful Adoption of Agentic AI Services" (May 2026)

### G. 行动授权、审计与成本治理

> **核心冲突**：Agent 能做的事越多，越需要分清"可以做""需要确认""永远不能做"。事故发生时，"Agent 自己做的"不是可接受的解释——需要完整审计链。同时，Agent 行动消耗 token 和人类注意力——成本需要被看见但不制造焦虑。

**服务于**：Goal 3（授权是安全的执行层）、Goal 2（成本治理影响进化方向）

**子问题**：

- **G1. 行动分类与授权**：哪些行动 Agent 自主执行（读文件）、哪些需要确认（修改配置）、哪些必须人工在场（发邮件、支付）、哪些禁止？多个低风险步骤如何检测组合高风险？

- **G2. 审计链完整性**：每条行动记录是否包含——谁发起、基于什么 belief、谁批准、什么工具、什么参数、影响了什么系统？审计链是否可回放（不只是日志，是可重放的行动链）？

- **G3. 事故学习闭环**：事故 → 还原根因 → 更新策略 → 更新 Agent belief → 更新组织流程 → 回归验证。如何让事故不只是被修复，而是让系统更不容易犯同类错误？

- **G4. 成本可见性与 UX**：用户什么时候看到 token/时间成本——实时？任务结束？超出预算时？成本信息的呈现方式会改变用户行为——实时计数器可能引发焦虑导致过早终止有价值的任务，任务结束的汇总可能引发"我花了这么多？！"的震惊。

- **G5. 内部内容溯源**：Agent 消费和生成的内容如何标记 provenance——来源、编辑历史、生成方式？如何在 summary、memory consolidation、report 中保留 provenance 而不是洗掉来源信息？

**Phase 2 范围**：
- 做：行动分类（可逆/需确认/需人在场/禁止）、审计链完整性、token 追踪与基本预估、内部 provenance metadata
- 不做：法律合规规则库、监管级审计报告、C2PA 集成

## 七领域与三目标映射

```
                    Goal 1(感知)  Goal 2(进化)  Goal 3(安全)

E. 多Agent协作                        ●            ○

G. 授权/审计/成本                     ○            ●
```

自进化(D)现在是独立一级领域，不再被埋在子问题里。B（信念/知识/记忆架构）是 D 的认知基础——没有 belief registry 和知识代谢，自进化就是盲目的。

三个目标各有至少一个"主场"领域：
- **感知**：A
- **自进化**：D（主）+ B（认知基础）+ C（执行基础）+ E（团队维度）
- **安全**：F（主）+ G（主）+ B（记忆安全）
