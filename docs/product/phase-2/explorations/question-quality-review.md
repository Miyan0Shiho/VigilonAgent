# 19 问题域质量审查

审查日期：2026-05-27
审查维度：可解性（现在能否解决）、覆盖缺口（遗漏了什么）、过度设计（哪些想多了）

---

## 逐领域审查

### 1. Intention Formation Gap

**可解性**：B-（部分可解，但核心问题很难）
- 环境感知 + 模式识别做主动建议 → 可解，研究基础已有（PASK、ProAgent）
- "帮助用户发现自己真正想解决的问题" → 这本质上是理解人类意图，是 AGI-complete 的
- 避免把用户训练成 prompt engineer → 更多是交互设计问题，可解

**过度风险**：低。这是入口问题，投入值得。

**盲区**：用户第一次打开 Vigilon 的前 5 分钟做什么？你的问题假设用户"有情境、有焦虑、有任务压力"，但如果用户是**完全不知道 Agent 能做什么**的新手，连情境都还没有？

---

### 2. Requirement Negotiation Before Execution

**可解性**：B（基本可解，但深度有限）
- 需求成熟度判断（是否矛盾、是否高风险）→ 可解，需要 checklist + 风险评估
- "主动提出替代目标" → 需要模型具备创造性推理，当前模型不稳定
- "区分说不清楚 vs 没想清楚" → 这是个很细颗粒度的判断，可能过度依赖模型能力

**过度风险**：中。4 个子问题都指向同一个高难度行为——Agent 像资深同事一样质疑你。现实是，当前模型即使能质疑，也经常质疑错方向。Phase 2 做到"风险评估 + 替代方案建议"就够了，"深度需求协商"需要模型能力再上一个台阶。

**盲区**：没有考虑**用户拒绝协商**的情况。如果用户说"不要问我，直接做"，Agent 应该如何降级？

---

### 3. Adaptive Stewardship

**可解性**：C+（较难，涉及深度用户建模）
- 新手 vs 专家的不同交互模式 → 可解，设计问题
- "判断用户需要引导、质询、代办还是放权" → 需要多维实时用户建模（熟练度、疲劳度、任务风险、时间压力），每个维度单独都可做，合在一起是产品复杂度噩梦
- "避免引导变打扰" → 核心 UX 挑战，需要大量迭代

**过度风险**：中高。四个角色（老师、秘书、翻译器、cockpit）的完整实现是一个产品线，不是一个 Phase 的功能。Phase 2 更现实的定位是：**一个可调节的介入阈值滑块 + 两个清晰模式（引导/静默）**，而不是完整的 4 角色自适应。

**盲区**：没有考虑**错误引导**的问题。如果 Agent 判断用户是新手给了详细引导，但用户其实是专家（判断错了），这种误判的代价是什么？

---

### 4. Collective Agency Governance

**可解性**：B-（工程部分可解，组织理论部分不可解）
- 决策权威、冲突保留、成本归因 → 工程问题，可解
- "Agent 造成损失，责任落在谁" → 这不是产品问题，是法律/组织设计问题。Vigilon 可以提供审计链，但**不能也不该替组织决定责任分配**
- 跨人类 owner 目标冲突 → 政治问题，Agent 应该显式化冲突然后升级，不应该"解决"

**过度风险**：高。问题 4 和 5（成本归因、责任归属）引入了组织治理和组织政治的话题——这些是真实的、重要的，但对 Phase 2 来说是**过早的复杂度**。Phase 2 应该聚焦 Agent-to-Agent 的协议（冲突如何记录、异议如何保留、信念如何背书），而不需要回答"企业里出事谁负责"。

**盲区**：没有考虑**Agent 数量和复杂度的爆炸**。如果 3 个 Agent 就好，那 30 个 Agent 的治理问题完全不同——通信复杂度 O(n²)、信念同步成本、决策延迟都会指数增长。

---

### 5. Long-Horizon Continuity

**可解性**：B+（相对可解，有明确的工程路径）
- 不可压缩核心、objective drift 检测、life segments → 这些是设计问题和工程问题，不是研究问题
- "数百次 compact 后证明约束没丢失" → 约束校验和是可实现的
- 三层存储分类（memory / artifact / belief ledger）→ 架构决策，可解

**过度风险**：低。这是接地气的问题，直接来自 Vigilon 已有的 compact 机制的运营痛苦。

**盲区**：没有考虑**跨 session 交接**。16 小时任务可能跨越多次用户上下线。用户下线 → 第二天回来，Agent 如何快速重建上下文让用户理解"我昨天做到了哪里，今天该做什么"？这和 Agent 内部的连续性不同——是**人-Agent 之间的连续性**。

---

### 6. Epistemic Discipline And Hallucination

**可解性**：B+（架构层面可解，模型层面不可解）
- Belief 带来源/证据/边界/过期条件 → 架构设计可解，BeliefMem、Kumiho 已验证
- 认知类别区分（事实/推断/假设/计划/偏好）→ 可解
- 信心门控 → 可解，但模型自评置信度的准确性本身不稳定
- 不确定性跨 compact 保留 → 架构可解

**过度风险**：低。这是整个问题地图中**最有洞察力的架构方向之一**。Belief registry 应该成为 Vigilon 的核心差异化设计。

**盲区**：没有考虑**假阳性克制**的问题。Agent 知道"我不知道"很重要，但同样重要的是 Agent **以为自己知道但实际上错了**——这比公开的不知道危险得多。Belief registry 需要标记的不是"不确定的 belief"，而是"高置信但可能错误的 belief"。

---

### 7. Deep And Dynamic Planning

**可解性**：B-（元数据结构可解，深度推理不可解）
- Plan 携带 horizon/confidence/risk/cost/pivot → 设计可解
- "什么时候重规划" → 规则可定义，但真正的判断需要模型理解"沉没成本"
- "继续执行会越来越错" → sunk cost detection 是好概念，但自动检测极其困难
- "多 Agent plan 比较/世界线分叉" → 概念强大，但工程复杂度高

**过度风险**：中。"世界线分叉"（worldline fork）是很吸引人的概念，但在 Phase 2 同时维护多条执行路径会让复杂度爆炸。更现实的定位：保留替代方案作为**未执行的 plan variant**，不是并行执行。

**盲区**：没有区分**微观规划**（下一步做什么）和**宏观规划**（整体方向）。Model 当前在微观规划上还行，宏观规划仍然很弱。这个问题域没有做这个区分。

---

### 8. Environment Adaptation

**可解性**：C+（领域分类可解，真正适应新环境很难）
- 环境感知协议 → 可解
- 领域风险分类法（red/yellow/green）→ 可解，但规则需要社区贡献
- "避免错误迁移代码工程经验" → 极其困难，本质上是 transfer learning 的负面案例
- Domain bootstrapping protocol → 可解

**过度风险**：中高。Vigilon 当前用户几乎全在代码工程环境。金融/工业/医疗/法务场景虽然重要，但对 Phase 2 是**远期的正确，近期的负担**。更务实的做法：把环境感知协议做好，让领域规则可由社区贡献，但 Phase 2 自己不建领域规则库。

**盲区**：没有考虑**多环境的混合场景**。一个项目可能同时涉及代码、配置管理、CI/CD、文档、Slack 沟通——这不是"一个领域"而是多个领域的混合。

---

### 9. Enterprise Safety, Rollback, And Incident Learning

**可解性**：A-（大比例可解，主要是工程问题）
- 可回滚性分类、blast radius、审计链 → 可解，Microsoft Agent Governance Toolkit 已有参考
- 事故还原 → Vigilon 的 transcript 机制已经是很好的基础
- 事故学习闭环 → 组织的部分不可控，但系统侧可做

**过度风险**：低。这是最"可工程化"的安全领域，有明确的业界参考。

**盲区**：没有考虑**安全机制的可用性成本**。每步都要审批 → 用户关掉安全。安全机制如果太沉重，用户会绕过它，结果比没有安全更糟。需要讨论安全摩擦（security friction）的可接受水平。

---

### 10. Adversarial Runtime Security

**可解性**：B（防御层可解，根本性解决不可解）
- 输入信任边界、指令来源分离 → 可解，AgentShield 等已有参考
- 间接 prompt injection → **不可根本性解决**——这是模型层面的问题，runtime 只能缓解
- Identity/Authority/Permission 绑定 → 可解，SPIFFE + 短生命周期 token
- 攻击后清理 → 可解

**过度风险**：低。OWASP ASI Top 10 给了清晰的框架，而且这是"做了就比不做好"的领域。

**盲区**：没有讨论**攻击检测的假阳性代价**。如果把正常用户指令误判为注入攻击并拦截，导致任务中断——这比漏掉一次攻击更影响用户信任。安全需要讨论 precision/recall tradeoff。

---

### 11. Knowledge Metabolism

**可解性**：B-（pipeline 可解，真正的知识评估很难）
- 可信度多信号评估 → 可解但信号质量参差不齐
- 浏览器 context 与 belief context 分离 → 可解，架构决策
- "知识 → 候选 belief → 验证 → accepted belief" pipeline → 可解
- "自动发现已有知识过期" → 核心困难。过期不是二元状态，是渐变的

**过度风险**：低中。知识代谢的隐喻很好，但完整实现（自动发现过期、自动重新验证、自动遗忘）是一个需要持续迭代的系统，不应期望 Phase 2 就做好。

**盲区**：没有考虑**知识冲突的呈现**。当 Agent 发现新知识和旧知识冲突时，用户看到的应该是什么？"我之前以为 X，现在发现 Y"还是静默替换？这涉及用户信任。

---

### 12. Agency Economics

**可解性**：A-（工程可解）
- Token 追踪、成本预估、贡献归因 → 工程问题
- 边际收益递减检测 → 可解但需要好的 heuristics
- 成本归因到项目/团队 → 可解

**过度风险**：高。Token budget 变成 political budget 的论述在智力上有趣，但对 Vigilon Phase 2 来说**过度抽象**。当前 Vigilon 用户更关心"我的任务花了多少 token"而不是"多 Agent 政治经济学"。Phase 2 做到 per-task, per-agent token 追踪 + 基本成本预估即可。

**盲区**：没有考虑**用户体验中的成本可见性**。用户应该在什么时候看到成本信息？消耗中实时显示 vs 任务结束后报告？成本信息的呈现方式会改变用户行为（看到正在烧钱 → 可能过早终止好任务）。

---

### 13. Memory, Personalization, And Context Ownership

**可解性**：B+（大比例可解）
- 所有权模型 → 可解
- 来源/时效/冲突/适用/撤销 → 可解
- consolidation 质量控制 → 部分可解，保留原始引用是关键
- 用户可见/可控 → 可解

**过度风险**：低。这是基础设施，值得投入。

**盲区**：没有考虑**memory 的 Git-like 版本控制**。Memory 会演化，用户可能需要"回到 3 天前的 memory 状态，那时候 Agent 的行为是对的"。

---

### 14. Agentic Web, Commerce, And Counterparty Trust

**可解性**：D（大部分依赖行业标准，Vigilon 单方面几乎不可解）
- 浏览器 context 来源分离 → 可解
- Agent identity standard → 不可单方面解决，需要 W3C/NIST/行业共识
- 交易证明链 → 需要银行/商家/支付系统的配合
- 外部数据 consent/license → 可解但依赖网站合作

**过度风险**：极高。这是 19 个领域中**最过度设计的一个**。Agentic Web 的核心问题（Agent identity、跨网站互操作、交易证明标准）是行业基础设施问题，一个开源 Agent runtime 无法单方面解决。Phase 2 应该聚焦**浏览器 Agent 的信任边界**（可解部分），其他做接口预留即可。

**盲区**：没有区分"Agent 浏览网页获取信息"和"Agent 代表用户在网页上行动"——这是两个完全不同的问题，前者的安全已经很难，后者的安全基本依赖行业标准。

---

### 15. Agent Management And Labor Recomposition

**可解性**：B-（管理工具可解，劳动重组不可解）
- 目标分解辅助、checkpoint、handoff protocol → 可解
- "人类是否只剩更难的工作" → 这不是产品问题，是社会问题
- "帮助用户成为 Agent manager" → 方向正确但太宏大

**过度风险**：中。劳动重组（labor recomposition）的论述让这个问题域从产品设计滑向了社会评论。对 Vigilon 有用的部分是：目标分解、进度管理、结果合并、handoff protocol。其余是白皮书内容，不是 Phase 2 工程。

**盲区**：没有考虑**Agent 做错了，用户如何纠正**。不只是"停止 Agent"，而是"Agent 误解了我的意图，如何在不重新开始的情况下纠正方向"——这是管理 Agent 最频繁的场景。

---

### 16. Operational Reliability, Evaluation, And Supply Chain

**可解性**：A-（大比例可解）
- 多维度 eval → 可解，Anthropic/OpenAI/Microsoft 已有参考
- 行为漂移检测 → 可解
- 供应链信任 → 可解
- Runaway 防护 → 可解

**过度风险**：低。接地气的工程问题，有明确的实现路径。

**盲区**：没有考虑**eval 的自动化成本**。完整的 eval suite 运行一次可能需要大量 token 和时间——如果每次发版都跑完整 eval，成本可能不可接受。需要讨论 eval 的分层策略（快速 smoke vs 完整验证）。

---

### 17. Legal Delegability And Regulated Action Boundary

**可解性**：C-（行动分类可解，法律合规不可解）
- 可委托性分类 → 可解
- 监管边界识别 → 需要法律专家 + 地区特定知识，不是软件产品能独立解决的
- 组合升级检测 → 可解

**过度风险**：高。行动分类框架是有用的，但"哪些行动只能建议""哪些需要人工在场""哪些不应被 Agent 执行"的精确答案取决于地区、行业、具体用例和法律解释。Vigilon 可以做的是：**提供分类框架 + 允许配置 + 默认 fail-safe**，而不是自己定义法律边界。

**盲区**：没有区分**法律责任**和**产品策略**。Vigilon 需要的是产品策略（"我们默认不允许 Agent 做 X"），而不是法律意见（"根据某法第 Y 条，Agent 不能做 X"）。前者是产品决策，后者需要律师。

---

### 18. Learning Burden And Super-Individual Divide

**可解性**：C+（工具可解，社会鸿沟不可解）
- 推理透明化 → 可解
- 技能追踪 → 可解
- "AI fluency 嵌入工作流" → 好的设计方向，但需要大量迭代
- "降低超级个体路径成本" → 社会愿景，不是产品 KPI

**过度风险**：中。超级个体鸿沟（super-individual divide）是社会趋势分析，对产品设计有方向性价值，但不应直接翻译为 Phase 2 feature。作为产品原则（"我们在设计时优先考虑普通用户"）是有用的；作为工程目标（"我们需要测量和降低超级个体鸿沟"）是过度抽象的。

**盲区**：没有考虑**学习负担的个体差异**。有些用户想学，有些用户只想完成工作。把学习嵌入工作流的前提是用户愿意在工作流中学习——这不一定成立。

---

### 19. Synthetic Content Provenance And Evidence Trust

**可解性**：C（provenance metadata 可解，完整生态不可解）
- 内容认知分类 → 可解
- provenance metadata → 可解
- C2PA/水印集成 → 依赖外部标准
- 跨系统 evidence provenance 联动 → 复杂但方向正确

**过度风险**：中高。Provenance 是重要的架构原则，但你描述的完整愿景（C2PA + watermark + citation + metadata + publisher trust 信号融合 + 与 belief/knowledge/incident/memory/legal 五个子系统联动）是一个需要数年构建的信息质量基础设施。Phase 2 应该做**内部 provenance metadata 标准 + 内容认知分类**，外部标准集成做接口预留。

**盲区**：没有考虑**provenance 的性能和存储成本**。如果每一条 belief 都带完整 provenance chain，存储和检索成本会显著增加。需要讨论 provenance 的深度策略（保留几层？什么情况下可以截断？）。

### 覆盖缺口（你没考虑到的重要问题）

**A. 结构性缺口——影响架构的问题**

1. **多模型适配与模型切换**
   当前 Vigilon 绑定了 DeepSeek。但模型在快速迭代——新模型出现、旧模型退役、不同模型在不同任务上表现不同。问题：Agent runtime 如何做到模型感知（model-aware）但不模型锁定（model-locked）？如何在不同模型间切换而不丢失 behavior consistency？

2. **Agent 数量爆炸的治理**
   你的问题假设 2-5 个 Agent 协作。但如果一个用户启动了 30 个 Agent 做不同任务，通信复杂度 O(n²)、信念污染风险、资源争抢、用户注意力过载——这些都是 3 个 Agent 时不存在的问题。

3. **安全机制的摩擦成本**
   每步都审批 → 用户关掉安全。安全检查太频繁 → 用户习惯性点"同意"。你需要讨论安全摩擦（security friction）的可接受水平，以及如何让安全检查不被用户视为阻碍。

4. **用户纠正 Agent 的交互机制**
   当 Agent 走错方向时，用户不只是想"停止"——用户想要"纠正"。如何用最小交互成本让 Agent 理解"你误解了，我其实是这个意思"？这可能是 Agent 管理中最频繁的场景。

**B. 体验缺口——影响用户接受度的问题**

5. **前 5 分钟体验**
   你的 19 个问题都假设用户有任务要做。但如果用户第一次打开 Vigilon，完全不知道 Agent 能做什么？前 5 分钟的体验决定了用户是否还会回来。

6. **Agent 能力发现**
   用户如何知道 Vigilon 里有哪些 Agent，每个能做什么？当 Agent 数量增长，可发现性会成为严重问题。这类似 app store 的发现问题但更复杂——因为 Agent 的能力边界是模糊的。

7. **成本感知的 UX**
   用户什么时候看到 token 消耗？实时计数器（可能引发焦虑）vs 任务结束摘要（可能引发震惊——"我花了这么多？"）。成本可见性的设计会塑造用户行为。

8. **跨 session 的人-Agent 连续性**
   你的领域 5 处理了 Agent 内部连续性，但没有处理"用户下线 8 小时 → 第二天回来 → Agent 如何快速让用户理解当前状态"。

**C. 远景缺口——Phase 2 不一定要解决但架构需要预留的**

9. **多模态感知**
   你的问题聚焦文本/代码，但随着多模态模型成熟，Agent 需要处理图片、音频、视频、图表。Belief registry 和 memory 结构需要考虑非文本内容。

10. **社区与共享**
    用户能否分享 Agent 配置、skill、memory 结构？如果没有社区层，每个用户从零开始配置是一种浪费；但有了社区层，供应链安全（领域 16）会更复杂。

11. **离线/气隙环境**
    某些企业环境不允许出网 API 调用。Agent runtime 能否在完全离线 + 本地模型的情况下运行？这会影响架构中的很多假设。

12. **Agent 失败模式分类**
    你的问题讨论了幻觉和安全，但没有一个系统性的 Agent 失败分类法：模式崩塌、目标错误泛化、奖励黑客、分布外失效、级联失败、确认偏差放大——理解 Agent **怎么失败**是设计安全机制的前提。

---

## 最终判断

### 19 个问题中：

- **保持当前深度**（5个）：6, 13, 5, 9, 10 —— 这些是 Vigilon 的核心架构差异化
- **缩界 50%**（6个）：4, 12, 14, 15, 17, 19 —— 方向对，但产品问题和社会/行业问题需要分开
- **需要重新聚焦**（2个）：3（从 4 角色到 2 模式）, 8（从跨行业到代码工程优先）
- **可以合并**：领域 1+2+3 有很多重叠（都涉及"执行前的理解和引导"），可以考虑合并为更大的 Stewardship 域；领域 9+10 也可以合并为 Security & Safety

### 遗漏的最大盲区是：

1. **多模型适配**（结构性，Phase 2 架构必须考虑）
2. **前 5 分钟体验**（体验性，决定产品能否留住用户）
3. **用户纠正 Agent 的交互**（体验性，最频繁的交互场景之一）
4. **Agent 失败模式分类法**（安全性，防御的前提是理解失败）
5. **安全机制的摩擦成本**（安全性，安全太重的系统会被绕过）

### 一句话总结：

你的 19 个问题在**深度和广度上都很好**——覆盖了从意图形成到内容溯源的完整链条，而且核心洞察（belief registry、adaptive stewardship、知识代谢、长程连续性）都是真正的差异化方向。主要问题是**大约 1/3 的领域把产品问题和社会/行业问题混在了一起**，需要做一次"什么是 Vigilon 能控制的、什么是需要行业协作的"的切割。另外有 5 个左右的结构性和体验性缺口需要补充。
