# 想法草稿：DeepSeek V4 的模型 + Claude Code 的架构 + Codex 的前端

> 文档定位：这是一份讨论底稿，不是设计方案，不展开实现，不做模块拆分，不给排期。  
> 目的：把我现在真正想要的东西先说清楚，方便后续讨论时不跑偏。

## 1. 我想做的到底是什么

我想要的不是“再做一个通用 AI Coding Agent”，也不是简单做一个 Claude Code 的换皮版本。

我现在脑子里最明确的一句话是：

**我想要一个以 DeepSeek V4 为核心模型能力、继承 Claude Code 的工作流架构、同时拥有 Codex 那种前端体验的代码代理产品。**

这三个部分在我心里不是并列拼装，而是分别承担不同角色：

- DeepSeek V4 负责模型能力本身，尤其是代码、推理、长上下文和成本效率。
- Claude Code 负责整体工作方式，也就是 agent 如何思考、规划、执行、申请权限、回填结果。
- Codex 负责前端感受，也就是用户怎么进入任务、怎么看过程、怎么接收反馈、怎么形成“产品感”。

所以这不是一句“换个模型就行”的话。

更准确地说，这是一个明确的产品组合偏好：

- 模型层，我更倾向 DeepSeek V4。
- 架构层，我更认可 Claude Code。
- 体验层，我更喜欢 Codex。

## 2. 为什么是这个组合

### 2.1 我想要 DeepSeek V4，不只是因为它便宜

DeepSeek V4 对我有吸引力，不只是价格问题。

我真正看重的是几件事：

- 它在代码和推理场景里已经足够强，至少值得被放到“主模型”位置来思考。
- 它的长上下文和推理能力，让它有资格承接 agent 这种复杂任务，而不是只做一个补充模型。
- 它更像是一个可以被围绕起来构建产品的模型，而不只是被接进一个聊天框里。

我不是想做一个“支持 DeepSeek 的 Claude Code”，而是想反过来思考：

**如果从一开始就把 DeepSeek V4 当成主角，那么整个 coding agent 产品应该长成什么样。**

### 2.2 我想要 Claude Code 的架构，因为它更像一个成熟的工作流

Claude Code 最打动我的，不是它是命令行工具，也不是它有多少工具调用。

真正让我认可的是它把 coding agent 这件事工程化了。

我想借的是它背后的工作流骨架，例如：

- 先理解问题，再决定是继续澄清、进入计划，还是直接执行。
- 把“计划”和“执行”区分开，而不是一上来就改代码。
- 对高风险动作设置明确的权限门槛，而不是默认模型什么都能做。
- 让工具调用、任务推进、状态反馈、上下文压缩形成一个闭环。

我喜欢 Claude Code 的地方，不是某一个按钮或命令，而是它背后的秩序感。

换句话说，我想保留的是 **agent 的思维流程和执行秩序**，而不是表面的命令名字。

### 2.3 我想要 Codex 的前端，因为它更像“产品”而不只是“工具”

Claude Code 的 TUI 很强，但它更像一个工程师原生工具。

Codex 给我的感觉不一样。它更接近一个完成度更高的产品界面，用户更容易理解当前发生了什么，也更容易形成“我在和一个可靠系统协作”的感受。

我想借的是 Codex 那种前端层面的优点：

- 更清晰的任务入口。
- 更自然的过程反馈。
- 更强的结果呈现和状态感。
- 更低的理解门槛。
- 更像产品，而不是只有开发者能看懂的系统界面。

所以我想要的不是“网页化 Claude Code”，而是：

**在不牺牲 agent 架构严肃性的前提下，把前端体验提升到 Codex 那种产品层级。**

## 3. 这不是简单的拼装，而是一种取舍表达

如果只用一句很短的话来描述这个方向，容易变成：

> DeepSeek V4 + Claude Code + Codex

但这句话太短了，容易让讨论跑偏，变成“把三个东西拼一起能不能做”。

我真正想表达的是：

- 我不想重复造一个纯聊天式的 AI IDE。
- 我也不满足于只把 Claude Code 的源码改成兼容别的模型。
- 我更想做的是一种新的组合：模型站在 DeepSeek 这一边，架构站在 Claude Code 这一边，产品体验站在 Codex 这一边。

这其实已经隐含了一种价值排序：

1. 先确定模型立场。
2. 再确定 agent 的工作方式。
3. 最后确定用户看到的产品形态。

也就是说，我不是先想“界面长什么样”，而是先想“这个系统应该怎么工作”，再去决定“用户应该怎么感知它”。

## 4. 为什么我现在想直接抄 Claude Code

我之所以会明确地产生“先抄 Claude Code”的想法，不是因为我单纯想走捷径，而是因为我已经为“从零摸索 agent 架构”这件事付出了真实的时间和成本。

一个非常直接的背景是：

**我曾经花了 90 美金，用编程工具去为我们一开始设计的 haibaraAgent 打造搜索链路。**

这件事本来代表的是一种比较理想化的路径：

- 我们先有自己的 agent 设想。
- 然后围绕自己的设想，一点点补齐搜索、执行、反馈、工具链路。
- 最终长出属于我们自己的系统。

但实际结果不是这样。

我投入了时间，也投入了钱，过程拉得很长，最后依然没有形成一个让我满意、可落地、可持续推进的结果。

这段经历对我最大的影响不是“亏了 90 美金”，而是让我更清楚地意识到：

**在 agent 这种系统里，最昂贵的往往不是模型调用本身，而是你在错误的架构探索路径上反复试错。**

所以我现在的判断发生了变化。

与其继续从一个相对模糊的自定义设想出发，边做边猜、边猜边改，不如先站在一个已经被验证过的成熟骨架上。

而 Claude Code 恰好代表了这样一种成熟骨架：

- 它已经证明了 coding agent 的基本工作流可以怎样被组织。
- 它已经把很多关键问题做成了工程化机制，而不是停留在 prompt 层面的想法。
- 它不是一个“概念上看起来对”的系统，而是一个“真正跑起来并被大量用户验证过”的系统。

所以对我来说，“抄 Claude Code”不是一句情绪化的话。

它更像一个阶段性策略：

- 先借用成熟设计。
- 先借用成熟代码实现。
- 先避免在底层工作流上重复踩坑。
- 等真正跑通以后，再考虑哪些地方值得重设计。

换句话说，我现在不是不想创新，而是不想把最宝贵的时间先花在重复发明那些已经被证明有效的基础秩序上。

## 5. 先抄，不等于永远没有自己的东西

我现在想得很清楚的一点是：

**先抄 Claude Code，并不意味着最终产品就只是 Claude Code 的翻版。**

我现在更接受一种分阶段的思路：

第一阶段，先借成熟系统把底层能力和基本工作流搭起来。  
第二阶段，再讨论什么地方应该重设计。  
第三阶段，再逐渐长出我们自己的产品语言、交互表达和模型气质。

也就是说，现阶段的“抄”，本质上是为了更快地跨过基础设施阶段，而不是为了放弃自己的判断。

我并不排斥后面重做。

恰恰相反，我只是觉得：

- 如果底层架构和执行秩序都还没有站稳，太早谈产品语言，很容易变成空的。
- 如果核心链路还没跑通，太早谈“我们自己的风格”，很容易只是包装层面的自我感动。
- 真正有价值的“自己的东西”，应该建立在一个已经可用、可靠、可推进的系统之上。

所以我现在愿意先承认一件事：

**我们现阶段最需要的，也许不是从零发明，而是先继承。**

先继承成熟架构，后表达产品个性；先继承工程秩序，后注入模型灵魂。

这可能才是更现实，也更节省时间的一条路。

## 6. 我当前不想过早进入的内容

这份文档刻意不讨论下面这些问题，因为现在太早：

- 不讨论技术栈选型。
- 不讨论前后端怎么拆。
- 不讨论是不是 TUI、Web、桌面端，还是三者混合。
- 不讨论 MCP、插件系统、沙箱、回滚等具体机制怎么做。
- 不讨论 Claude Code 的哪些源码能直接复用，哪些要重写。
- 不讨论第一版 MVP 范围。
- 不讨论开发顺序和排期。

这些当然都重要，但它们现在都属于“方案层”。

我现在更想先固定的是“我到底偏爱什么样的产品组合”和“我觉得什么东西应该放在中心位置”。

## 7. 我心里的核心判断

到目前为止，我的几个核心判断大概是这样：

### 7.1 模型不该只是后端供应商

如果产品核心能力真的来自模型，那么模型选择会反向塑造架构和体验。

所以 DeepSeek V4 不是一个可以最后再替换的组件，而应该是一开始就参与定义产品边界的核心变量。

### 7.2 Claude Code 真正难抄的是架构秩序，不是界面

很多人会觉得 Claude Code 的亮点是 TUI、工具调用、权限确认、命令体系。

但我现在越来越觉得，真正难的是它背后的秩序：

- 什么情况下先计划。
- 什么情况下先澄清。
- 什么时候可以自动推进。
- 什么时候必须把控制权交还给人。

如果这个秩序没有学到，外面做出来的东西即使功能看着像，也只是“能调用工具的聊天机器人”。

### 7.3 Codex 的价值不是“好看”，而是产品叙事更完整

我不是单纯觉得 Codex 的界面更漂亮。

我更在意的是它在产品感上的完成度，它让用户更容易理解任务、过程、结果、状态，以及系统现在是在想、在做、还是在等你。

这是一种叙事能力，不只是视觉设计。

### 7.4 现阶段“先继承再重设计”比“从零定义一切”更现实

haibaraAgent 的搜索链路探索让我更清楚一件事：

很多时候，真正拖慢产品的不是“没有想法”，而是基础工作流始终没有稳定下来。

所以至少在当前阶段，我更认同这样的路径：

- 先把成熟系统的骨架接过来。
- 先把关键链路跑通。
- 先获得一个能工作的 agent。
- 然后再决定哪些部分必须属于我们自己。

这不是放弃原创性，而是把原创性放在更合适的阶段发生。

## 8. 我希望后续讨论围绕什么展开

如果后面要继续讨论，我更希望问题围绕这些方向，而不是直接进入怎么做：

- DeepSeek V4 作为主模型，究竟会把这个产品的气质带向哪里。
- Claude Code 架构里，哪些是“必须保留的骨架”，哪些只是 Anthropic 语境下的实现。
- Codex 的前端到底有哪些关键体验值得借，而不是只学页面样式。
- 这个组合最终会导向一个什么样的产品身份：工程师工具、通用 coding agent，还是面向更广泛开发者的产品。

## 9. 一句话版本

如果后面我要用一句话来和别人讨论这个方向，我希望不是：

> 我想做一个仿 Claude Code 的东西，换成 DeepSeek 模型。

而是：

> 我想做一个以 DeepSeek V4 为核心模型、采用 Claude Code 式 agent 架构、并拥有 Codex 级产品前端体验的 coding agent。

这两句话看起来接近，但其实不是一回事。

前一句更像“替换供应商”。

后一句才更接近我现在真正想表达的产品方向。
